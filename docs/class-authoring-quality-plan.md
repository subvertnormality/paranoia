# Behavioral class authoring and bounded performance investigation

## Frozen operating model
One trusted local operator and OS run the MCP server and authenticated reviewer CLIs.
Repository, plan and provider bytes are untrusted static data. Reviewers inspect but do
not execute repository-selected code; the implementing agent may run the authorized
isolated calibration/tests. Ordinary edits invalidate bindings. Existing provider CLI
network boundary; no external factual claims or web research in this card. Three parallel
census lanes and sequential consolidation/correction/final; small fixtures through
thousands of files, tens to low hundreds of claims, evidence useful within minutes.
False clearance, wrong evidence binding and incorrect blocking authority have high
impact; recoverable blocking is acceptable. Exclude hostile races, compromised OS,
multi-tenancy, corrupted-state recovery and formal proof. The operating contract preserves
all existing reviewer roles/calls, cold independence, native retries and timeout caps;
later sections refer to this authority rather than redefine it.

## Next speed and architecture gate
S1. After Q1-Q5, rank current-source provider critical-path work from retained telemetry:
context preparation, repeated repository exploration, output, scheduling and retries.
Respect historical-version qualifications. Use prompt/schema/raw channels and call spans;
do not equate tokens or summed concurrent durations with elapsed savings. Existing
sub-6% local overhead is insufficient reason for another local-only optimization campaign.

S2. Select at most one materially promising scheduling/context/retry candidate, preserving
the operating contract, load-bearing context and evidence authority.
Before implementation or paid comparison, freeze its concrete change, representative
matched workload, sources/settings/order, all time/cost accounting, correctness controls
and qualification in a separate design card. Check the mechanism deterministically before
a bounded paired native comparison. Target at least 20% end-to-end time or cost reduction
with neither materially worse; no broad claim from one mode, a microbenchmark or favorable
subset. If no candidate warrants testing, publish the measured stop decision instead.

S3. Consider refactor/rearchitecture only for demonstrated root causes or bottlenecks.
Prefer one authoritative representation or simpler existing boundary over new subsystems.
Below the speed gate, demonstrated bug reduction or substantial maintenance/reasoning
simplification at high confidence can warrant a separately accepted design. Priority is
20%+ speed, bugs, maintainability, easier reasoning. No broad rewrite, provider/model/
effort downgrade, operating-contract weakening, new persistence or unsupported
quality claim. Issues #49/#50 are not automatically closed by this work.
