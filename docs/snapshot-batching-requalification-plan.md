# Native snapshot batching requalification

## Objective and boundary
Requalify the preserved native batching implementation against the current-main baseline defined by B3. The original 7360f40 experiment and its failed live gate remain immutable historical records; this is a new explicit contract and campaign after the decision-evidence admission fix. Deliver one measured repository-setup improvement toward issues 49 and 50: separate typed Git object acquisition from inert filesystem rendering, and remove per-file process startup. The broader semantic-handler decomposition and model/convergence latency remain follow-on work, not acceptance claims for this card.

Operating model: one trusted local operator and OS; repository, plan and provider bytes are untrusted static data. Ordinary edits must invalidate snapshots or block/retry. Reviewers never execute repository-selected code. Existing provider CLI and public HTTP boundaries remain unchanged. Three structural census lanes may run concurrently; arbitration retains separate inert workspaces. Expected workloads include hundreds to several thousand files and tens to low hundreds of claims, with evidence useful within minutes. False clearance, authority mistakes and wrong evidence binding have high impact; recoverable blocking is acceptable. Exclude hostile same-user races, compromised OS, multi-tenancy and intentionally corrupted-state recovery.

## Architecture obligations
A1. Add one small typed native-object reader. A request binds an exact full hexadecimal object ID and expected blob size from the pinned tree inventory. Keep all Git execution routed through inert_git; do not introduce a daemon, persistent cache, custom subprocess transport, repository code execution or new Git-version floor.

A2. Obtain the recursive NUL-delimited tree inventory with object sizes. Keep byte-exact paths distinct from request IDs: only validated ASCII object IDs enter the batch input. Materialization continues to reject unsafe paths, unsupported tree entries and invalid IDs. Symlinks remain marker-plus-target inert regular files; executable files remain non-executable; gitlinks remain inert markers. This is the authoritative baseline-equivalence contract: manifest entries, ordering, rendered file bytes, permissions and history must match the baseline.

A3. Partition requests deterministically into native cat-file batches capped at 128 objects and 8 MiB of expected payload. A single larger blob occupies its own batch and remains complete; this is a grouping target, not a truncation or repository-size limit. Do not collect a whole repository of blobs in memory. Account separately for bounded per-object framing overhead. Avoid new persistence and lifetime complexity.

A4. Validate the entire returned batch before admitting its contents: exact requested order and ID, blob type, declared size equal to the inventory, complete payload, delimiter, full Git blob digest and absence of trailing output. Missing/promised objects, wrong type, malformed/truncated frames, bad hashes or failed commands fail closed. No filter/textconv/follow-symlink/lazy-fetch fallback may run. Preserve the existing inert launcher environment.

A5. Preserve A2 through materialize and evidence_workspace. Every caller retains its own immutable tree and cleanup boundary, with failure admission as defined in B2. No reviewer prompt/schema, provider settings, claim/class checks, convergence transitions, final obligation, model-call topology or durable schema changes are included. Beneficiary modes and permitted claims are defined only by C1 below.
